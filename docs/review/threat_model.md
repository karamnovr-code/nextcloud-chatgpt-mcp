# Bounded predeployment threat model

Review snapshot: 2026-09-18. Scope: auth_provider.py, nextcloud.py, server.py,
jobs.py, worker.py, doc_engine.py and their tests. Production deployment was not
present at the initial inspection. No private files, upstream checkout, secrets,
or virtualenv source files were read; only the virtualenv interpreter was executed.

Assets: owner's Nextcloud files, immutable source folders, native OAuth grants,
generated documents, and service availability. Trust boundaries: anonymous public
HTTP to FastMCP OAuth; downstream signed token to upstream owner identity check;
relative user paths to fixed-origin DAV; untrusted document bytes to native
parsers; generated bytes to authenticated create-only DAV write.

Entry points: OAuth registration/authorization/token endpoints; MCP tool inputs;
Nextcloud filenames/XML listing and document bytes. An attacker can plausibly
influence a document received by the owner. Anonymous attackers should never gain
MCP data access. Owner tool authorization does not make incoming document code
trusted. Remote links/formulas must not gain execution through conversion output.

Intended controls observed: exact ChatGPT redirect allowlist; persistent encrypted
OAuth state; fixed HTTPS owner verification; bearer forwarding only to fixed DAV
origin, without redirects or environment proxy use; strict path segment handling;
allowlisted roots and blocked aliases; no delete tool; create-only writes and
downloaded SHA-256 verification; isolated Office rendering; per-worker resource
limits and explicit pagination.

Initial uncertainty: generic worker process had scrubbed environment but shared
service filesystem/UID/network; parent is adding full worker namespace isolation.
No exploit of native parsers was attempted or claimed. Deployment mounts, service
identity, inbound auth middleware and a real ChatGPT OAuth round trip need separate
live acceptance. Mock transport tests are not that acceptance.
